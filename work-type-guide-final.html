How to Categorise
Your Work
A practical guide to the four work types. Use this every time you create a ClickUp ticket. Getting this right gives us real visibility into where our time goes.
The Most Important Idea
The category is not about what the work looks like. It is about why it arrived and what it does for us. A bug fixed on a schedule is Planned. The same bug discovered broken on a Tuesday is Unplanned. Same artifact — different category.
Why Bother — What The Data Buys You
Projects fall behind because Unplanned work consumes capacity that was mentally allocated to Planned work — invisibly, with no record of why the plan slipped. After four weeks of proper logging you can say: 40% of our time went to fires, here are the components that keep breaking, here is the Improvement work we need to stop that. Without the data you are guessing. With it you have an argument.
Three Rules Before You Create Any Ticket
No Ticket = No Work

If it is not a ticket, nobody works on it. Threshold: any work that takes or took longer than 30 minutes needs a ticket. Below that is noise. Above that is data you need.

Capacity Is Protected

At least 50% of the team's time is reserved for Planned work each sprint. Consuming that with Change or Unplanned work requires explicit sign-off, not a Slack message.

New Priority = Name The Trade-Off

Nothing new enters the sprint without explicitly naming what it displaces. Not "we'll fit it in." What specifically gets pushed out.

Split Compound Work

If work spans two categories, create two tickets. Do not blend a refactor and an emergency fix into one.

The Inbox Model
Inbox Cadence

Triage person reviews the inbox at least once per working day. Developer tickets arrive mostly correct. Requester tickets need classification. Both need a title check.

Fallback Rule

If unsure which type to select, submit anyway. Unplanned is the safe default for anything that interrupted you. Triage corrects everything else. Submitting wrong beats not submitting.

Triage Authority

Triage person can reassign work type and send a ticket back for a better title. The form is the only valid submission channel. Slack messages are not tickets.

Pattern Recognition

The triage person sees everything across all types. Three Unplanned tickets on the same component in two days should become an Improvement ticket before the fourth arrives.

Decision Tree & The Four Categories
Step 1 — Use This Decision Tree For Every Ticket
1
Did this work arrive outside the planning cycle and force you to stop what you were doing?
Yes → Unplanned No → Q2
Urgency alone does not make something Unplanned. An urgent task you scheduled into the sprint is still Planned.
2
Is this a consciously chosen piece of work that creates a new capability, feature, or page that did not exist before?
Yes → Planned No → Q3
3
Is this operational work — keeping the site current, correct, or running — that creates no new capability for users?
Yes → Change No → Q4
It does not need to be recurring. A first-ever price update on a new product is still Change — operational, not new capability.
4
Is this internal only — no customer ever interacts with the output — and does it make the team's future work faster or cheaper?
Yes → Improvement
Step 2 — The Four Categories
Category 1
Planned
Roadmap work you chose. Builds something new for users.
  • PC configurator / builder tool
  • New laptop product line page
  • Trade-in programme page
  • Product comparison feature
  • Wishlist / save build feature
  • Warranty portal for customers
  • Bundle deals section
  • Redesigned checkout flow
Category 2
Unplanned
Work that chose you. Arrived outside the planning cycle. Interrupted everything.
  • Checkout broken, orders failing
  • Payment gateway is down
  • Product images not loading
  • Price showing incorrectly
  • Add to cart not working
  • Order confirmation emails not sending
  • Site down during campaign launch
  • Configurator crashing on GPU select
Category 3
Change
Routine operational tasks. Keeps things running. Builds nothing new.
  • Homepage banner swap (new promo)
  • Adding a new PC / laptop SKU
  • Updating specs on a product page
  • Price change across product range
  • Updating stock availability
  • Seasonal sale assets (11.11, CNY)
  • Updating shipping rates or zones
  • Refreshing FPS / benchmark numbers
Category 4
Improvement
Internal. Users don't see it. Makes the team faster or cheaper in future.
  • Improve page speed (Core Web Vitals)
  • Refactor old configurator code
  • Automated testing for checkout
  • Internal tool for product listings
  • Document the banner deploy process
  • Fix analytics gaps in GA4
  • Reduce image sizes / CDN optimisation
  • Clean up duplicate / unused code

Real Examples — How One Task Creates A Chain

One piece of work can create a chain reaction across categories. Notice how a Change or Planned task with no risk gate generates Unplanned work — and how Unplanned work reveals what Improvement is needed.

Example 1 — Russian Characters Removed From Code
Change
Remove Russian characters from the codebase. Looked like a trivial, routine cleanup task. No impact score. No test plan.
Unplanned
The change broke XML parsing. Not tested. Site broke without warning.
Unplanned
Emergency fix required. All planned work stopped. Team scrambled to diagnose and repair.
Improvement
Add blast radius scoring to all Change tickets. High-blast-radius changes require a test plan before shipping.
What This Teaches Us

The Change looked trivial so no one assessed its risk. Any Change touching shared code, XML, or data pipelines must carry a blast radius score. If the score is High, it cannot ship without a test plan and review.

Example 2 — New Features Slowing Pages
Planned
New features added to product pages across several sprints. Each one shipped and looked fine individually. No page speed gate on any ticket.
Unplanned
Pages become noticeably slow. Page speed scores drop. Nobody planned to deal with this — it accumulated silently.
Unplanned
Time spent investigating, diagnosing, and fixing performance. Roadmap work paused.
Improvement
Record page speed score before and after every Planned and Change ticket. If score drops beyond threshold, ticket cannot be marked Done without sign-off.
What This Teaches Us

Unplanned work is not only caused by bad Changes. Planned work shipped without a performance gate does the same damage. Page speed must be recorded in the ticket — before and after — not just checked when something feels slow.

One Rule Per Category — Memorise These Four
Planned
We chose this work and it creates something new for users.
Unplanned
The work chose us. It arrived outside the planning cycle and interrupted everything else.
Change
We do this regularly. It keeps things running, but nothing new is built.
Improvement
Users cannot see it. It makes the team's future work faster or cheaper.
